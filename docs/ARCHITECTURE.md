# Architecture

SwiftUI provides the native sidebar, library thumbnails, task table, device setup, settings, and menu bar. PhotoKit streams originals from the local/iCloud library. Swift owns batch scheduling, disk and device guards, backoff metadata, and ServiceManagement login registration.

The embedded Rust executable owns Motion Photo preparation, paired-resource validation, SHA-256 hashing, ADB delivery, and the SQLite queue (bundled rusqlite). ExifTool reads and updates metadata; macOS avconvert transcodes incompatible motion video to H.264. Runtime Python is not required.

The subprocess boundary currently uses CLI arguments, JSON queue/device responses, and labeled preparation/transfer output. It is not yet a versioned streaming protocol. Output is collected into a temporary file to prevent pipe-buffer deadlocks; operations have timeouts.

Queue commands serialize through a filesystem lock; SQLite WAL with synchronous FULL atomically commits the latest `jobs` row and append-only `events` entry. Single-asset operations use the asset primary key, without replaying all history. Swift updates the affected queue row from each transition response, retaining full-list refresh only on startup/batch entry. Retry metadata stays in Swift's atomic JSON file. Stable identifiers derive from PhotoKit local identifiers, which are local-library identifiers rather than a portable cross-Mac identity.

Schema v1 migrates the legacy JSONL inside a single transaction. Complete records are replayed in order; an interrupted final line remains in the exact `queue.legacy.jsonl` backup and its length is recorded in metadata. Malformed complete records abort migration. Only after the backup is synced and the database committed is `queue.jsonl` atomically replaced with a protocol-2 marker that the old executable refuses. A crash before sealing is recovered using the saved source hash, without reimporting. A changed source after commit, missing/corrupt database or unknown schema stops processing rather than silently starting over. Copy all of State after quitting the app; active WAL files can contain committed progress.

ADB delivery uses a hidden partial file, remote SHA-256 verification, rename, media scanning, and a final hash. Matching remote files skip copying and receive media scanning again. `transferred` is the last automatically recorded phase; cloud observation phases are not automatically inferred from time or file arrival.

Mac cache reclamation runs after a durable delivery transition and before subsequent batches, within the app's batch lease. The Rust `reclaim-cache` command holds the queue lock while checking a completed record, validated hash and asset-specific remote path, and freshly hashing that Pixel file. It derives the removable directory as `Staging/SHA256(assetID)` and refuses symlinks/special files. It never removes queue state, orphan/quarantined directories, Apple Photos or Pixel files. Partial deletion can be retried using the retained journal proof; missing directories are a no-op. Errors retain the completed transfer state. The old-cache sweep only includes identifiers still present in the current Photos scan and stops after three verification failures per batch. Swift budget accounting deduplicates hard links; already-prepared outgoing bytes are reserved on Pixel without charging Mac cache twice.

The transport can later be replaced by a Pixel companion, but current device discovery, temperature/storage checks, delivery, and hashing require ADB. Long-running large-library operation still requires reliable cloud evidence and Pixel-side space reclamation.

## Pixel cleanup coordination

The opt-in cleanup adapter and transfer admission share one `pixelReserveGB` floor. Admission adds each pending file and concurrent reservation. A low-space failure cancels and drains workers before cleanup, preserving prepared files. The model persists `pixelCleanupHoldDevice` and `pixelCleanupTransferBytes` so subsequent batches and restarts keep the required recovery budget. No opportunistic transfer path bypasses a cleanup wait.

`pixelCleanupPendingDevice` is written immediately before the official UI action; `pixelCleanupLastAction` starts the ten-minute action interval at the same boundary. Earlier `pixelCleanupLastAttempt` values are ignored because they included failed preflight checks. Pending actions are reconciled before any space-based release. Confirmed completion with insufficient space retains the hold. External/manual space recovery can release an unstarted hold; explicitly disabling the experiment clears that hold but preserves uncertain operations.

Cleanup failures carry semantic message keys to both the overview and log. No-eligible-copy waits, foreground-app waits, temperature values, remaining cooldown and required recovery space have separate messages. Setup still navigates without deleting; the adapter requires the official safe-backup confirmation UI before a destructive action.

Cleanup eligibility comes from Google Photos' official device-cleanup confirmation, which must explicitly state that the selected items are safely backed up. Global backup completion is not required; Google Photos may still be uploading other items. PixelBridge pauses its own transfers during cleanup, observes the completion page, then measures free space before resuming.

Before committing a cleanup action, an unrecognized navigation page can trigger one force-stop and relaunch of Google Photos, followed by a fresh account and official confirmation check. A fresh UI read and device preflight precede recovery. Persisted pending actions, observed cleanup progress/completion, account mismatches and cancellation block this restart. Final confirmation and completion polling are outside the restart path. UI idle failures retry fresh snapshots up to three times without force-stopping the app. Recovery stages are shown in the UI and log.

The cleanup adapter emits transient stage events before navigation and reads real percentages only from the recognized Google Photos progress node. The model publishes the same semantic message to the overview, footer and Experiments while logging stage changes instead of every poll. Completion clears pending cleanup before attempting the recognized Done action; return-navigation failures do not invalidate completion or repeat cleanup. All transient UI progress is cleared on exit.

## Activity log retention

A serial background queue appends runtime messages to daily UTC log files under `State/Logs`, rotating individual files at 5 MB. Settings persist retention (1–90 calendar days, default 7) and total storage (10–500 MB, default 50). Writes, startup reads and exports prune expired files and then the oldest files over budget. Lowered limits apply at the next such operation; the UI keeps only 200 recent entries in memory and previews 15. The legacy `State/activity.log` is copied once before removal, with its modification day preserved. An export waits behind accepted writes and streams retained files into a temporary text file before replacing the user-selected destination. Failures leave source logs intact and surface in the UI.

## Skipped transfer tasks

`skipped` is a durable SQLite queue phase. Undelivered, inactive tasks can be skipped individually or as a filtered failure set. Skip changes preserve files and queue history. A skipped task can only return through an explicit transition to `failed`; resume, rescans and bulk retry do not include skipped rows. Candidate execution checks current skip/mutation state again so a stale batch snapshot cannot start a newly skipped task.

The scan, original lookup and thumbnails use the same PhotoKit fetch options, including all burst members. Missing assets/resources and unsupported formats stop automatic retries immediately; other item-specific failures stop after five consecutive failures. Environmental interruptions do not consume this budget. A failed durable queue write stops the batch instead of swallowing the error. A stop is not evidence that the original was deleted: limited library access and library changes can make an asset inaccessible. Users can restore the task after resolving the issue.

### Outstanding asset-access investigation

The reported missing-asset errors have not been tied to specific asset identities or resource types. The log display names are not unique identifiers. Verify affected local identifiers against the current library with consistent fetch options, then inspect burst membership, media subtypes, resource types, hidden state and authorization. Distinguish lookup failure from unavailable iCloud resources and export failure. Preserve queue identity and originals during diagnosis. No claim of deletion or resolved root cause follows from the new skipped state.

## Structured diagnostics

Activity messages remain short and localized. `diagnostic-YYYY-MM-DD-NNNNNN.jsonl` stores schema-1 diagnostic records beside the activity files. Both streams share the configured retention and total storage budget. Diagnostic records are encoded and written on the logger's serial background queue; they never appear in the 200-entry activity preview. Export includes both streams, with section headers identifying each source file. Parse the lines inside a diagnostic section as independent JSON objects.

Each record contains a UTC timestamp, event, process-session ID, optional batch and attempt IDs, a SHA-256 task reference (`assetRef`), allowlisted string fields, and an optional error chain. The task detail disclosure shows the full reference; failure messages show its first 12 characters. References persist across attempts on the same Photos asset identity; batch/attempt UUIDs distinguish repeated attempts and concurrent work. Attempt numbers reflect the consecutive-failure budget, not the lifetime attempt count.

Attempt records distinguish started, prepared, completed, failed, deferred and cancelled work. Fields identify the operation, prior queue phase, elapsed time, retry/skip decision, retry deadline, configuration and authorization. Scan-time metadata is a compact in-memory value; only assets actually attempted are written. The export path adds current lookup options/result count, asset flags/dimensions, resource types/UTIs/extensions (first 12 resources plus total count), download budget, cached-resource flags and prepared size as those facts become available. It does not guess cloud availability, deleted status or the cause of an empty fetch. A failed lookup can be compared with scan-time metadata even when no current resource list is accessible.

NSError domain/code and the underlying chain (up to three nested causes) are retained without serializing arbitrary userInfo. Friendly mapped device errors keep their original cause; subprocess failures include the exit status under `PixelBridge.Process`. Queue-write failures are recorded separately from the original item failure. Cleanup stage changes and failures carry semantic stage/error keys without recording UI XML, account labels or every percentage poll. Successful Pixel delivery explicitly records that Google cloud backup is not verified.

Diagnostics cannot recover context from older logs. To investigate a previously skipped asset, explicitly restore that task, reproduce once, then export logs. No change to the retry policy, Photos originals or cleanup authorization is implied by diagnostic collection.
